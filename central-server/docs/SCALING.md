# 수평 확장 & 용량 계획 (차수 16 #236/#245)

> 설계 메모 — 현재는 단일 인스턴스로 충분. 본 문서는 성장 시의 확장 경로와 용량 가정을 기록한다.

## 1. 현재 아키텍처의 확장 한계
- **상태(state)**: 프로바이더 WS 세션은 **인스턴스 로컬 메모리**(`ConnectionRegistry`)에 있다.
  → 인스턴스를 늘리면 한 인스턴스가 보유한 세션을 다른 인스턴스가 알 수 없다(라우팅 분절).
- **DB**: Postgres 는 수평 확장과 무관하게 공유(요청/사용량/정책 영속화).
- **요청 흐름**: 유저 `/ask` → (그 길드 프로바이더가 붙어 있는) 인스턴스에서 라우팅 → 에이전트.

## 2. 수평 확장 경로(#236)
세션이 인스턴스 로컬이라는 점이 핵심 제약. 단계적 옵션:

1. **sticky by guild(권장 1단계)**: 한 길드의 모든 프로바이더·유저 트래픽을 같은 인스턴스로
   고정(예: `hash(guildId) % N`). 길드 단위 격리(이미 보장)와 자연스럽게 맞물린다.
   - 장점: 세션 공유 인프라 불필요. 단점: 길드 단위 부하 불균형 가능.
2. **세션 레지스트리 외부화(2단계)**: WS 연결 자체는 인스턴스 로컬이되, "어느 길드의 프로바이더가
   어느 인스턴스에 있는가"를 Redis 등에 두고 인스턴스 간 **요청 포워딩**.
   - 라우팅 요청이 들어온 인스턴스 → 해당 프로바이더 보유 인스턴스로 내부 호출.
3. **메시지 브로커(3단계)**: 추론 요청/응답을 브로커(예: NATS/Redis Stream)로 교환해 인스턴스
   토폴로지와 무관하게 라우팅. 가장 유연하나 운영 복잡도 최고.

> 결론: 베타~초기 운영은 **단일 인스턴스** 또는 **sticky-by-guild** 로 충분. 2/3단계는 동시
> 프로바이더 수가 단일 인스턴스 한계(아래)를 넘을 때 착수.

## 3. 용량 가정(#245)
대략적 1인스턴스 기준(보수적 추정, 실측으로 갱신 필요):

| 자원 | 가정 | 근거/비고 |
|---|---|---|
| 동시 WS 세션 | ~수천 | 세션당 메모리 작음(상태머신+맵). JVM 힙·FD 한도가 1차 제약 |
| 동시 추론 in-flight | 프로바이더 합산 `maxConcurrency` | 실제 병목은 **프로바이더 PC** 처리량 |
| 요청 레이트 | RateLimiter(유저 분당) + 풀 크기에 종속 | 중앙은 I/O 바운드(추론은 에이전트가 수행) |
| DB | 요청/사용량 write 위주 | HikariCP 풀 크기·인덱스로 조정 |

병목은 거의 항상 **중앙이 아니라 프로바이더 PC의 추론 처리량**이다. 중앙 스케일 전에
프로바이더 수·`maxConcurrency`·모델 부담 수준을 먼저 점검한다.

## 4. 용량 신호(언제 스케일하나)
- `providerpool_active_connections` 가 수천에 근접 / JVM 힙·GC 압박 상승.
- 라우팅 지연(p95) 상승, 큐(`maxQueue`) BUSY 빈발.
- DB 커넥션 풀 포화(HikariCP 대기).

→ 위 신호가 지속되면 §2 의 sticky-by-guild 부터 적용한다.
