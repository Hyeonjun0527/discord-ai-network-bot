# NEXA Provider Agent — 데스크톱 앱 화면정의 (ASCII)

> 데스크톱 Provider Agent 앱의 전체 화면 와이어프레임 정의.
> 모든 화면은 **같은 뼈대**를 공유한다. 정렬보다 **구조 전달**을 우선해서 본다.
> (한글은 모노폰트에서 2칸을 먹어 오른쪽 테두리가 약간 들쭉날쭉할 수 있음)

---

## 디자인 시스템 (공통 규칙)

- **상단바**: `● ● ●` + `◆ NEXA Provider Agent` + 우측 버전(`v0.31.0`)
- **좌측 사이드바**: 로고 → 상태뱃지(`● AI 제공 중`) → 6개 전역 탭
  - 활성 탭은 **왼쪽 `┃` 액센트**로만 표시 (빈 원 ❌)
- **상태 점 언어 통일**
  - `●` 켜짐 / 정상 / 제공 중
  - `○` 꺼짐 / 미사용
  - `⏸` 일시중지
  - `⚠` 승인 대기 / 오류
- **콘텐츠는 카드 기반**
- **위험 작업(`제거` 등)은 절대 즉시 버튼 ❌** → `⋯` 메뉴 + 확인 모달
- **서버 내부 화면(07~13)**: `서버` 탭 활성 상태에서 상단에 **서버 상세 서브탭**이 깔림

# 서버 상세 (서버 탭 → 카드 클릭)

> **권한 모델 결정(2026-06-07 개정)**: 데스크톱 앱은 **기부자 + 관리자 도구를 겸한다**.
> - **기부자 화면(07)**: 누구나 보는 "이 서버에 대한 내 기여 현황 + 내 self-service 정책".
> - **관리자 화면(08~13)**: 관리자는 **이 앱에서 직접** 관리한다(채널 AI·RAG·프리셋·다중응답·역할 정책·
>   Provider 승인). ~~웹 대시보드 위임~~은 **폐기**(2026-06-07). 모순이었다 — 승인 대기(PENDING)·기부자는
>   웹조차 못 여는데 "웹에서 관리"는 성립하지 않는다.
>
> **승인 대기(PENDING) 규칙**: 아직 승인 전이라 **기여 현황·정책·관리 모두 숨기고** 승인 대기 안내만 보인다.
>
> **백엔드 관리 채널 / Gap-M (2026-06-07 구현)**: provider-agent ↔ central 관리 채널을 HTTP 로 뚫었다.
> - central `ProviderAdminController`(`/provider/admin/{approve|reject|remove|manage}`): **durable 토큰 신원**
>   + **JDA 관리자 판정**(`BotGuildLister.isGuildAdmin` = MANAGE_SERVER|ADMINISTRATOR) 2단 게이트 →
>   기존 `ProviderRegistrationService` 호출(슬래시·웹과 동일 서비스·감사 로그). 권한 상승 불가.
> - provider-agent: `_post_provider_admin` + `admin_manage`/`admin_action`, webui `GET /api/servers/{g}/manage`·
>   `POST /api/servers/{g}/providers/{action}` 프록시(앱 → webui → central).
> - **role 별도 전달 불필요**: 앱은 `serverManage` 응답 ok 로 관리자 여부 판정(비관리자는 ok=false) — `AuthOkFrame`
>   확장 회피. 와이어 무변경(HTTP body DTO).
> - **남은 것**: ① 로스터/대기 목록의 이름·모델·today 보강(central 은 현재 providerId·state 만 — 이름/통계는
>   Discord/집계 소스 결합 후속) ② 관리 정책 토글(autoApprove)은 슬래시 명령만(관리 API 미노출). 프로토타입은
>   이상적 shape 를 mock 으로 확정해 둔다.

## 백엔드 Gap (이 화면을 실데이터로 채우려면 central-server 가 줘야 할 것)

> 프로토타입은 mock 으로 먼저 검증하고, 아래가 채워지면 `USE_MOCK=false` 로 전환.

- **Gap-R (role 전달)** — `AuthOkFrame`(또는 sync 응답)에 **서버별 내 역할**(`ADMIN`/`PROVIDER`)을 실어야
  "웹 대시보드 열기" 노출 여부를 결정할 수 있다. 현재 `guildId/guildName` 만 있음.
  판정 자체는 백엔드에 있음(`Permission.MANAGE_SERVER | ADMINISTRATOR`, DiscordBot.kt) — **전달만** 추가.
- **Gap-S (서버별 내 기여 통계)** — 서버별 `todayRequests`, `avgLatencyMs`, 내가 이 서버에 제공 중인
  모델 목록, `members`(Discord 길드 멤버수). 현재 홈 전역 통계만 있고 **서버 단위 분해**가 없음.
- **Gap-P (내 self-service 정책 read/write)** — 이 서버에 대한 **내** `dailyLimit`/`maxConcurrency`/
  `maxSeconds`/`scope` 를 **읽고 쓰는** provider-agent API. 백엔드 로직은 있음
  (`ContributionPolicyService`, `ProviderProtectionService`) — **provider-agent 채널로 노출**만 필요.
- **Gap-W (웹 대시보드 딥링크)** — 관리자용 웹 대시보드의 **서버별 URL**(`https://…/dashboard/{guildId}`)
  스킴 확정. 앱은 이 URL 을 외부 브라우저로 연다.

## 설계 포인트

- **관리/기여 분리** — 앱은 "내 기여(read + self-service)", 관리자 정책은 "웹 대시보드(위임)".
  이미 있는 웹 어드민과 **중복 0**.
- **self-service 만 앱에서 쓰기 가능** — 일시중지/재개·내 한도·내 범위(`/provider-*` self 명령의 GUI).
  다른 Provider·서버 정책은 앱에서 **읽기조차 안 함**(권한 밖).
- **role 은 노출 제어용** — 관리자에겐 "웹 열기" 버튼, 기부자에겐 "권한 필요" 안내.
  앱이 관리 기능을 직접 수행하지 않으므로 보안 경계가 단순(앱은 토큰 권한 이상을 못 함).
- **상태 점 언어 유지** — `●` 제공 중 / `⏸` 일시중지 / `⚠` 승인 대기.
- **PENDING 서버** — 내 제공이 시작 전이라 정책/일시중지 컨트롤을 숨기고 승인 대기 안내만.
