# Provider Pool 민감 정책 — 품질 향상과 Provider PC 보호

이 문서는 **함께 만드는 AI 네트워크**인 Nexa에서, Provider Pool 기반 답변 품질을 높이는 기획과 **타인의 로컬 PC 에 과부하를 주지 않기 위한 안전 정책**을 함께 정의한다.

연결 문서:

- [Provider Pool 민감 질문 30개](./SENSITIVE_QUESTIONS.md)

핵심 원칙:

- 이 서비스는 “함께 만드는 AI 네트워크”이지만, 여러 사람의 CPU/GPU 를 합쳐 하나의 거대한 모델을 돌리는 분산 추론 시스템은 아니다.
- 중앙 서버는 질문을 적절한 Provider 의 로컬 AI 로 보내고, 결과를 받아 Discord 에 전달한다.
- 사용자 수가 늘어날수록 좋아질 수 있는 것은 “물리적으로 합쳐진 성능”이 아니라 **선택지, 안정성, 라우팅 품질, fallback 능력**이다.
- 어떤 품질 개선도 Provider 의 동의·한도·가용성·보호 정책을 넘어설 수 없다.

## 1. 품질 향상 기획의 허용 범위

### 가능한 개선

- **모델 능력 기반 라우팅**: 어려운 질문은 더 큰 모델/전문 모델을 가진 Provider 에게 우선 배정한다.
- **질문 유형별 라우팅**: 코딩, 한국어, 요약, 긴 글, 빠른 응답 등 요청 성격에 맞는 Provider 를 고른다.
- **Provider 품질 점수**: 응답 성공률, 평균 지연, 사용 가능 모델, 사용자 피드백, 반복 실패율을 점수화한다.
- **fallback**: 선택된 Provider 가 실패하면 같은 조건의 다른 Provider 로 제한적으로 재시도한다.
- **선택적 다중 응답**: 고난도 질문에서 여러 Provider 답변을 비교하거나 합성하는 모드를 실험할 수 있다.

### 명시적 비목표

- 여러 유저 PC 의 CPU/GPU 를 합쳐 하나의 큰 모델을 실행하는 기능.
- 사용자의 명시적 동의 없이 여러 Provider 에게 같은 질문을 대량 발송하는 기능.
- 품질 향상을 이유로 Provider 의 개인 한도·휴식·일시정지·시간대 설정을 우회하는 기능.
- Provider 를 “무제한 무료 계산 자원”처럼 쓰는 운영 방식.

## 2. 위험 모델

Provider Pool 에서 가장 위험한 실패 모드는 중앙 서버가 의도치 않게 **타인의 PC 에 대한 부하 증폭기**가 되는 것이다.

대표 위험:

- 한 사용자의 반복 질문이 여러 Provider 에게 퍼져 사실상 DDoS 처럼 동작한다.
- 고난도 질문 하나가 다중 응답/재시도/fallback 을 거치며 과도한 GPU/CPU 사용을 만든다.
- 악성 사용자가 긴 프롬프트, 반복 요청, mention spam 으로 Provider PC 를 계속 깨운다.
- Discord 서버가 커질수록 특정 고성능 Provider 에 요청이 몰린다.
- “품질 점수”가 높은 Provider 만 계속 선택되어 선의의 기여자가 피로해진다.
- Provider 가 배터리/발열/업무 중 상태인데 중앙 서버가 이를 무시한다.

따라서 안전 정책은 품질보다 우선한다.

## 3. Provider 보호 원칙

- **명시적 동의**: Provider 는 직접 참여해야 하며, 서버/길드 단위 토큰으로만 연결된다.
- **언제든 중지**: Provider 는 `/수신정지`, 에이전트 종료, 서버 탈퇴, 봇 제거 등으로 즉시 중지할 수 있어야 한다.
- **기본 보수성**: 기본 동시 처리 수는 낮게 시작한다. 고성능 장비라도 자동으로 무제한 확장하지 않는다.
- **한도 우선**: 일일 한도, 동시 한도, 가용 시간, 배터리/부하 보호가 라우팅보다 우선한다.
- **부하 분산**: 좋은 Provider 에 몰아주지 말고, 최근 처리량·휴식 시간·실패율·부하를 반영한다.
- **투명성**: Provider 는 내 PC 가 언제, 얼마나, 어떤 수준의 요청을 처리했는지 볼 수 있어야 한다.
- **비밀 보호**: 민감정보가 Provider PC 로 갈 수 있음을 사용자에게 알리고, Provider 로그에는 프롬프트 원문을 남기지 않는다.

## 4. 요청 증폭 방지 정책

### 기본 요청

- 기본 질문은 **Provider 1명**에게만 보낸다.
- 실패 시 fallback 은 기본 **1회**로 제한한다.
- 같은 요청이 동시에 여러 Provider 에게 발송되지 않도록 requestId 단위 중복 방어를 둔다.

### 다중 응답/품질 비교 모드

다중 Provider 응답은 매우 조심스럽게 다룬다.

- 기본값은 꺼둔다.
- 관리자 또는 정책이 허용한 채널/역할에서만 켠다.
- 사용자가 “고품질/비교 모드”임을 인지할 수 있어야 한다.
- 요청 1건당 fan-out 상한을 둔다. 초기값은 최대 2명, 실험 후에도 3명을 넘기지 않는다.
- 다중 응답은 Provider 의 남은 한도·현재 부하·가용 시간·최근 처리량을 모두 통과해야 한다.
- fan-out 을 썼다면 사용량/기여량/부하 비용을 실제 처리한 Provider 별로 정확히 기록한다.
- 같은 Provider 에게 연속으로 고난도 요청을 보내지 않도록 cooldown 을 둔다.

### 재시도/fallback

- 실패 원인이 사용자 입력/권한/정책 문제이면 fallback 하지 않는다.
- Provider 일시 장애/타임아웃이면 제한적으로 fallback 한다.
- fallback 후에도 실패하면 추가 확산하지 않고 명확한 실패 안내를 보낸다.
- 타임아웃 직전의 느린 Provider 에게 같은 요청을 계속 재시도하지 않는다.

## 5. Rate limit 과 쿼터

최소 정책:

- 사용자별 분당 요청 수 제한.
- 채널별 분당 요청 수 제한.
- 길드별 전체 동시 요청 제한.
- Provider 별 동시 요청 제한.
- Provider 별 일일 처리량 제한.
- Provider 별 heavy/restricted 요청 제한.
- 동일 사용자→동일 Provider 연속 배정 제한.
- 긴 프롬프트/첨부/다중 응답은 더 높은 비용으로 계산.

권장 기본값은 운영 데이터가 쌓이기 전까지 보수적으로 둔다. 제한 완화는 실제 지표와 Provider 피드백을 본 뒤에만 한다.

## 6. 품질 점수와 공정성

Provider 품질 점수는 “좋은 사람에게 더 많은 일을 시키는 점수”가 아니다. 점수는 다음 요소와 함께 사용해야 한다.

- 모델 적합도
- 성공률
- 평균 지연
- 현재 부하
- 남은 일일 한도
- 최근 처리량
- 최근 휴식 시간
- 실패율/타임아웃율
- 사용자 피드백
- Provider 가 설정한 부담 수준

금지:

- 품질 점수만으로 계속 같은 Provider 를 고르는 것.
- 고성능 Provider 의 한도를 자동으로 올리는 것.
- Provider 가 쉬는 시간인데 품질 점수가 높다는 이유로 깨우는 것.

## 7. Abuse 대응

의심 상황:

- 같은 유저가 짧은 시간에 많은 질문을 보냄.
- 같은 질문을 여러 채널/mention 으로 반복.
- 극단적으로 긴 프롬프트나 무의미한 토큰 반복.
- 실패를 유도하는 요청으로 fallback 을 계속 발생시킴.
- 특정 Provider 를 노리고 고부하 요청을 반복.

대응:

- 사용자/채널/길드 단위 rate limit.
- 반복 실패 요청의 fallback 차단.
- 긴 프롬프트 비용 상향 또는 거절.
- 관리자 알림과 감사 로그.
- 임시 사용자 차단/채널 차단.
- Provider 자동 보호: busy/limited/paused/unhealthy 전환.

## 8. 운영 지표와 알림

필수 지표:

- Provider 별 CPU/GPU/메모리/배터리 신호 또는 agent 가 보고 가능한 부하 지표.
- Provider 별 분당 요청 수, 일일 처리량, heavy 요청 수.
- Provider 별 평균 응답 시간, 타임아웃, 실패율.
- fallback 발생률, fan-out 사용률.
- 사용자/채널/길드별 요청량.
- rate limit hit 수.
- 자동 pause/limited/unhealthy 전환 수.

알림 조건:

- 특정 Provider 에 요청이 과도하게 몰림.
- fallback/fan-out 이 급증.
- heavy 요청이 평소보다 급증.
- Provider 실패율/타임아웃율 급증.
- 길드 전체 요청량이 비정상적으로 증가.

## 9. 출시 게이트

품질 향상 기능을 켜기 전 필수 조건:

- kill switch 로 즉시 비활성화 가능.
- 다중 응답/fan-out 기본값 off.
- Provider 별 동시/일일/heavy 한도 적용.
- 사용자/채널/길드 rate limit 적용.
- Provider pause/resume/leave 가 항상 우선.
- 부하/배터리 보호가 라우팅 전에 적용.
- abuse 탐지 로그와 운영 알림 준비.
- 실제 Discord smoke test 완료.

## 10. 사용자 안내 원칙

사용자에게는 어렵게 설명하지 않는다.

권장 안내:

> 이 봇은 여러 사람의 컴퓨터를 하나로 합쳐 쓰는 방식이 아니에요.
> 질문에 맞는 커뮤니티 멤버의 로컬 AI 가 답변을 만들고, Nexa가 그 결과를 전달합니다.
> 더 좋은 모델을 가진 멤버가 많아질수록 더 적합한 AI 를 고를 수는 있지만, 각 멤버의 컴퓨터는 정해둔 한도 안에서만 안전하게 사용됩니다.

Provider 안내:

> 내 컴퓨터는 내가 허용한 범위 안에서만 사용돼요.
> 원할 때 언제든 멈출 수 있고, 과부하가 감지되면 자동으로 쉬게 됩니다.
