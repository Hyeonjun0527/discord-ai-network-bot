# Provider Pool 민감 질문 30개

이 문서는 커뮤니티 로컬 AI Provider Pool 을 처음 보는 사용자가 의심하거나 문제 삼을 수 있는 질문을 미리 정리한 것이다. 제품 안내, 도움말, 운영 FAQ, 관리자 대응 문구의 기준으로 사용한다.

## 1. 구조와 오해

1. **다른 사람 컴퓨터 자원을 몰래 빌려 쓰는 건가요?**  
   아니요. Provider 가 직접 참여하고 토큰으로 연결한 경우에만 사용됩니다. 언제든 멈출 수 있어야 합니다.

2. **여러 사람의 CPU/GPU 를 합쳐서 하나의 큰 AI 를 돌리는 건가요?**  
   아니요. 질문 하나를 적절한 Provider 의 로컬 AI 에 보내고, 결과만 받아 Discord 에 전달하는 구조입니다.

3. **사람이 많아지면 자동으로 더 똑똑한 AI 가 되나요?**  
   직접적으로 그렇지는 않습니다. 다만 더 좋은 모델을 가진 Provider 를 고르거나, 질문 유형에 맞는 Provider 를 찾을 가능성은 높아집니다.

4. **내 질문이 모든 Provider 에게 뿌려지나요?**  
   기본 정책은 Provider 1명에게만 보내는 것입니다. 다중 응답은 별도 정책과 제한이 있는 실험 기능이어야 합니다.

5. **품질을 높인다고 여러 PC 에 같은 질문을 동시에 보내면 DDoS 처럼 되는 것 아닌가요?**  
   그래서 fan-out 은 기본 off, 제한된 상황에서만 최대 2명 수준으로 시작해야 하며 rate limit 과 Provider 한도가 우선합니다.

## 2. Provider PC 보호

6. **내 컴퓨터가 갑자기 과부하로 느려질 수 있나요?**  
   가능성을 낮추기 위해 동시 처리 수, 일일 한도, heavy 요청 제한, 부하/배터리 자동 보호가 필요합니다.

7. **내가 게임하거나 작업 중인데 AI 요청이 들어오면 어떡하죠?**  
   Provider 는 가용 시간, 일시정지, 에이전트 종료로 언제든 쉬어야 합니다. 부하가 높으면 자동 제한도 걸려야 합니다.

8. **노트북 배터리가 닳아도 계속 쓰나요?**  
   배터리 상태를 감지할 수 있으면 자동 pause/limited 로 전환하는 것이 정책입니다.

9. **내 PC 가 뜨거워지거나 팬이 계속 돌면 누가 책임지나요?**  
   기본 책임은 서비스를 보수적으로 운영하는 데 있습니다. 그래서 기본 한도는 낮게 시작하고 Provider 가 직접 멈출 수 있어야 합니다.

10. **고성능 PC 를 가진 사람만 계속 희생되는 구조 아닌가요?**  
    품질 점수만으로 몰아주면 안 됩니다. 최근 처리량, 휴식 시간, 한도, 현재 부하를 반드시 함께 반영해야 합니다.

11. **내가 설정한 한도를 서버 관리자가 마음대로 무시할 수 있나요?**  
    무시하면 안 됩니다. Provider 의 개인 한도와 일시정지는 라우팅 점수보다 우선해야 합니다.

12. **에이전트를 켜두면 밤새 계속 요청이 올 수 있나요?**  
    가능성을 막기 위해 일일 한도, 가용 시간, 자동 보호, rate limit 을 둡니다. 원하면 에이전트를 종료하거나 수신정지해야 합니다.

## 3. 보안과 개인정보

13. **내 PC 에 외부에서 접속할 수 있게 포트를 여나요?**  
    아니요. 에이전트는 중앙 서버로 outbound WebSocket 연결만 합니다. inbound 포트 개방은 필요하지 않습니다.

14. **중앙 서버가 내 파일을 읽거나 명령어를 실행할 수 있나요?**  
    아니요. 정책상 임의 shell, 파일 접근, 임의 URL 호출은 금지해야 합니다. 에이전트는 로컬 Ollama 추론 요청만 처리해야 합니다.

15. **질문 내용이 Provider 에게 보이나요?**  
    로컬 AI 가 답변하려면 질문은 Provider PC 로 전송될 수 있습니다. 그래서 비밀번호, API 키, 개인정보는 입력하지 말라고 고지해야 합니다.

16. **Provider 가 내 질문을 저장할 수 있나요?**  
    정책상 Provider agent 로그에는 프롬프트 원문을 남기지 않아야 합니다. 다만 타인 PC 로 전송되는 구조라는 점은 사용자에게 명확히 알려야 합니다.

17. **민감정보를 실수로 보냈으면 어떻게 하나요?**  
    즉시 해당 키/비밀번호를 폐기·교체해야 합니다. 봇은 민감정보 입력 금지를 반복 고지해야 합니다.

18. **관리자는 누가 어떤 질문을 했는지 다 볼 수 있나요?**  
    운영에 필요한 최소 기록만 남겨야 하며, 프롬프트 원문 저장은 피해야 합니다. 사용량·상태·오류 중심으로 기록하는 것이 원칙입니다.

19. **Provider 가 악의적으로 이상한 답변을 보내면요?**  
    Provider 실패율, 신고, 사용자 피드백, 관리자 차단/제거 기능이 필요합니다. 중요한 답변에는 검증 안내가 필요합니다.

20. **Provider 가 내 질문을 이용해 프롬프트 인젝션이나 악성 응답을 할 수 있나요?**  
    가능성을 완전히 0으로 만들 수는 없습니다. 그래서 신뢰 가능한 커뮤니티, 관리자 승인, Provider 차단, 민감정보 금지, 답변 검증 안내가 필요합니다.

## 4. 공정성·운영·남용

21. **누군가 봇을 스팸처럼 호출하면 Provider PC 가 공격받는 것 아닌가요?**  
    사용자/채널/길드 rate limit, mention spam 방지, 반복 요청 차단, 관리자 차단 정책이 필요합니다.

22. **긴 프롬프트를 계속 보내면 비용이 Provider 에게 전가되는 것 아닌가요?**  
    긴 프롬프트와 heavy 요청은 더 높은 비용으로 계산하고 한도를 더 빨리 소진하게 해야 합니다.

23. **실패할 때마다 다른 Provider 로 계속 재시도하면 요청이 퍼지지 않나요?**  
    fallback 은 기본 1회로 제한해야 합니다. 사용자 입력/권한/정책 오류는 fallback 하지 않습니다.

24. **다중 응답 비교 기능은 Provider 여러 명을 동시에 쓰는 거라 위험하지 않나요?**  
    위험합니다. 그래서 기본 off, 명시적 허용, fan-out 상한, Provider 한도 적용, 운영 알림이 필요합니다.

25. **한 서버가 너무 커지면 작은 Provider 들이 감당 못 하지 않나요?**  
    길드 전체 동시 요청 제한, 채널별 제한, Provider 별 한도, 모델 부담 수준별 라우팅으로 감당 가능한 요청만 보내야 합니다.

26. **관리자가 마음대로 내 PC 를 서버 전체 공용 자원처럼 홍보하면요?**  
    Provider 참여는 자발적 기여이며, 각자의 한도 안에서만 쓰인다는 안내가 필요합니다. 무제한 공용 자원처럼 표현하면 안 됩니다.

27. **기여순위가 있으면 사람들이 과도하게 경쟁하지 않나요?**  
    기여순위는 인정/감사 목적이어야 하며, 과부하를 유도하는 경쟁 지표가 되면 안 됩니다. 한도와 휴식이 우선입니다.

28. **서버에서 봇을 삭제하면 Provider 는 어떻게 되나요?**  
    해당 서버의 Provider 세션, 등록, 미사용 토큰은 정리되어야 합니다. 기여 기록은 감사 기록으로 남길 수 있습니다.

29. **내가 서버를 나갔는데도 Provider 로 남아 있으면요?**  
    서버 멤버십 정합성 검사로 등록과 세션을 정리해야 합니다. 이미 남긴 기여 로그는 유지할 수 있습니다.

30. **문제가 생겼을 때 바로 끌 수 있나요?**  
    가능해야 합니다. 품질 라우팅, 다중 응답, pseudo-streaming 같은 위험도가 있는 기능은 각각 kill switch 를 가져야 합니다.

## 사용자에게 보여줄 짧은 안내문

> NEXA는 여러 사람의 컴퓨터를 하나로 합쳐 쓰지 않아요.
> 질문에 맞는 커뮤니티 멤버의 로컬 AI 가 답변을 만들고, NEXA가 결과를 전달합니다.
> Provider 의 컴퓨터는 본인이 허용한 한도 안에서만 사용되고, 언제든 멈출 수 있어요.
> 비밀번호, API 키, 개인정보 같은 민감정보는 절대 입력하지 마세요.
